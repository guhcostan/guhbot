# Guh Bot reference research and REA verification

Research date: 2026-10-17. This is a source-inspection snapshot, not a claim that
the desktop, mobile client or hosted deployment passed an end-to-end test.
Implementation and deployment work can supersede the gaps below.

## Primary sources and product requirements

| Source | Verified observation | Requirement for Guh Bot |
|---|---|---|
| [Grok Bot](https://x.ai/bot) | Its official page describes desktop and iOS clients, parallel bots, persistent context, approval requests, teach-once routines and website sign-in. Its FAQ says bots share one persistent cloud computer per user. | One durable host with several agents and remote clients. Shared user workspaces are a valid baseline; a VM per bot is not required for this reference model. |
| [MausBot](https://mausbot.com/) | The site distinguishes free local desktop/mobile companions from paid hosting. Phones connect to the machine that actually runs agents; a sleeping local host cannot continue working. It describes existing agent subscriptions/API keys, connected apps and computer access. | Explain local versus hosted operation, provider charges and host availability. Pairing must not suggest that the phone itself runs the agents. |
| [OpenMausBot source](https://github.com/milind-soni/OpenMausBot) | Its public repository identifies an Apache-2.0 project with Electron, mobile companion, deployment files and an evaluation harness. | Distribute independently implemented source, installation instructions and reproducible deployment tooling. Evaluate agent outcomes as well as protocol correctness. |
| [agentes.chat](https://agentes.chat/) | Public HTML metadata describes agents with roles, tools, budgets and an accountable person, working visibly in channels and requesting approval for sensitive actions. | Treat roles, execution visibility and approval ownership as product concepts. Budget enforcement needs an implementation before it becomes a product promise. |
| [REA](https://github.com/morluto/rea) and [JavaScript workflow](https://github.com/morluto/rea/blob/main/docs/javascript-application-workflows.md) | REA supports local static JavaScript/Electron analysis without launching the target. Its documentation distinguishes evidence from runtime verification. | Study interface behavior locally, retain limitations, and reimplement independently. |

The web retrieval tool could not read agentes.chat. A direct HTTPS GET returned
its 5,638-byte HTML shell; the metadata above was read from that shell, not from
an authenticated session or a functioning agent run. A Python urllib request
received HTTP 403 while curl succeeded. No accounts were created and no forms
were submitted during this research.

  136 `person`, 36 `background`. These counts were recalculated today. They are
  an existing extracted interface inventory, not 172 relationships independently
  proven by today's bounded REA run.
- The corrected coordinator's interface table is readable in
  `recon/beautified/node-agent-coordinator.beauty.js`, around lines 32,800 onward.
  The teach-recording and host-settings interfaces occur in that table.
- [The dossier index](re/00-index.md) references an older full-run evidence file
  `recon/rea/js-application.json` that **is absent in this checkout**. Its summary
  and stderr remain. Do not describe that missing file as presently inspected.
- `recon/FINDINGS.md`, section E1, records a corrected two-byte ASAR extraction
  error. The older REA evidence and some dossier line numbers were generated
  before correction. The claim in [desktop architecture](re/01-desktop-architecture.md)
  that leading stray bytes belong to the shipped app is superseded by E1.
- The reference's `person`/`background` classifications concern box wake/parking
  authority according to the existing dossier correction. Guh Bot uses these
  names for device authorization. Similar names do not establish equivalent
  security semantics.

Today's run proves static analyzability of the corrected coordinator. It does

## Security finding requiring resolution before exposure

At inspection, `devices.unlock` was classified `background` without `localOnly`
in `packages/protocol/src/methods.ts`. Its handler in
`packages/host-core/src/host.ts` accepted a fixed, public string as local-presence
proof, then promoted the calling paired device to `person`. The dispatcher did
not impose a separate presence gate. This contradicts the README's claim that a
paired device cannot promote itself.

Require a host-side operator authorization boundary, reject promotion from
ordinary paired network clients, and add a regression test exercising that exact
network path. Do not turn a client-supplied assertion into authority. The main
implementation task was notified of this finding; check its final code and test
results for resolution.

## Delivery priorities

1. Close the device-promotion issue before opening a hosted gateway.
2. Prove desktop and mobile against the same live host, with an explicit flow for
   granting mobile control and revoking it.
3. Deploy and verify durable hosted operation plus a real waitlist submission.
4. Publish installable artifacts and reproducible self-host instructions with
   accurate provider and availability requirements.
5. Implement demonstrated-action recording and actual multi-agent handoffs before
   claiming behavioral parity. Keep voice, desktop control and sign-in work
   visible as separate remaining capabilities.

## Implementation follow-through

The unlock finding in this report was repaired in the October 17 implementation: `devices.unlock` is local-only, and a paired viewer cannot call `devices.setAccess`. Explicit operator delegation is a separate person-authorized method. The host reloads device access on every request; revocation also closes event delivery. Regression tests cover remote unlock refusal, delegation, demotion and revocation.

The mobile client now supports secure remote and tenant paths, and the desktop includes bot creation, device management and pairing QR. The gateway catalog and tenant credentials survive restarts. These changes do not establish feature parity with Grok Bot. Voice, VNC, full routine recording, subagent orchestration and managed billing remain out of scope for this release.
